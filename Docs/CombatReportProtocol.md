# 전투 리포트 서버와 Unity 연동 규격

SW는 캐릭터별 명중 부위 전송과 사망 후 리포트 UI를 구현한다. 서버는 실제 적용 피해를 집계하고 사망 시 고정된 본인 기록을 제공한다. 기존 데미지, 보호막 처리, 킬·어시스트·헤드샷 처치 통계, 보상과 기존 패킷 크기는 변경하지 않는다. 새 클라이언트 작업은 아직 포함하지 않았다.

## 이번 구현 범위

- 라운드 초기화 또는 부활부터 본인 사망까지, 상대·방향·무기/스킬별 피해와 명중 횟수를 메모리에 집계한다.
- 체력 피해와 보호막 피해를 분리한다. 합계가 총 피해이며 남은 체력·보호막을 초과한 피해는 제외한다.
- 총기 및 기존 근접무기 피격 경로, 드론 테이저, 이니시에이터 궁극기, 엔트리 블레이드, 센티널 궁극기의 실제 HP 피해를 기록한다.
- 사망을 일으킨 마지막 피해까지 기록한 후 고정한다. 사망 후 남아 있는 스킬이 주는 피해는 죽은 시전자 본인의 리포트에 추가하지 않는다. 살아 있는 피해자의 수신 기록에는 포함된다.
- 라운드 초기화, 부활, 방 변경·퇴장 때 이전 기록을 비운다. 다음 경기 및 계정 데이터에 누적 저장하지 않는다.
- 부위별 데미지 배율은 도입하지 않는다. 현재 머리·몸통·다리는 동일한 기존 무기 데미지를 적용한다.
- 서버가 승인한 피격 처리의 기록이다. 클라이언트가 보고한 총기 명중 부위를 서버 히트박스·탄도로 재검증하는 안티치트 구현은 아니다.

## UI 요청 순서

1. 기존 `SC_DIE(122)`에서 `deadPlayerId == MyPlayerId`일 때 관전 화면 한쪽에 리포트 영역을 열고 첫 페이지를 요청한다. 서버는 새 리포트를 자동 발송하지 않는다.
2. `CS_COMBAT_REPORT_REQUEST(370)`에 현재 roomId, 새 requestId, lifeId=0, pageIndex=0을 보낸다. 상대의 playerId를 요청하는 필드는 없다.
3. `SC_COMBAT_REPORT(371)` 성공 응답의 lifeId를 저장한다. 추가 페이지는 동일 roomId와 lifeId, 증가한 pageIndex로 요청한다.
4. 성공한 모든 페이지를 받은 후 상대별로 묶어서 표시한다. 접었다 펼칠 때는 캐시를 재사용한다. 매 프레임 조회하지 않는다.
5. 관전 대상이 바뀌어도 본인의 리포트를 유지한다. 상대의 현재 체력·위치·보유 무기 상태는 표시하지 않는다. sourceId는 해당 피해를 일으킨 당시 무기/스킬이다.
6. 기존 라운드 리셋, 부활, 로비/방 이동 및 연결 종료 이벤트에서 UI와 캐시·대기 요청을 모두 초기화한다. 결과씬 표시가 필요하면 클라이언트에서 이미 받은 기록을 보관할 수 있지만, 이번 서버 API는 경기 전체 리포트가 아니다.
7. 응답은 requestId, roomId, lifeId 및 클라이언트의 현재 사망 상태와 대조한다. 이전 라운드에 보낸 요청의 늦은 응답으로 UI를 다시 열지 않는다. 로컬 라운드/부활 세대도 대기 요청에 묶어 관리한다.

살아 있는 플레이어·관전자·다른 방에서는 리포트를 조회할 수 없다. 미인증 요청은 기존 인증 게이트에서 응답 없이 거절한다. 잘못된 패킷 길이 역시 무시한다. 타임아웃 시 빈 기록을 사실처럼 표시하지 말고 조회 실패 상태를 표시한다.

## 기존 피격 패킷 확장

`PKT_CS_HIT = 120`, 전체 **9바이트**, 기존 순서와 크기를 유지한다. 모든 오프셋은 헤더를 포함한 시작 기준이다.

| 오프셋 | 타입 | 이름 | 의미 |
| --- | --- | --- | --- |
| 0 | uint16 | size | 9 |
| 2 | uint16 | type | 120 |
| 4 | uint32 | targetId | 피격 대상 playerId |
| 8 | uint8 | hitZone | 0 몸통, 1 머리, 2 다리 |

3 이상은 클라이언트 총기 피격 패킷에서 허용하지 않는다. `부위 없음=3`은 서버가 스킬 리포트에만 사용한다. 옛 클라이언트의 0/1 전송은 그대로 작동한다.

Unity에서는 기존 `SendHit(uint targetPlayerId, bool isHeadshot = false)`를 제거하지 말고 유지한다. 새 `SendHit(uint targetPlayerId, HitRegion region)` 오버로드를 추가하고 기존 bool 메서드가 새 메서드의 Body/Head로 위임하도록 연결한다. 새 region을 다시 bool로 변환하면 다리 정보가 소실된다.

캐릭터 본을 따라가는 히트박스와 부위 컴포넌트는 프리팹 Hierarchy에 저장한다. 팔·손은 Body, 허벅지·종아리·발은 Legs로 통일한다. 각 캐릭터의 실제 스케일·앉기·애니메이션에서 검증한다. 이동용 캡슐이 전용 히트박스보다 먼저 총알을 차단하지 않는지 확인한다.

## 전송 공통 규칙

- Little-endian, pack=1. C# 기본 구조체 정렬·bool·가변 문자열을 그대로 직렬화하지 않는다.
- 기존 PacketHeader는 size:uint16 + type:uint16, 총 4바이트다.
- TCP 수신은 기존 누적 버퍼에서 size만큼 완성된 프레임을 분리한 후 읽는다. 한 번의 Receive와 한 패킷이 같다고 가정하지 않는다.
- 새 enum 값은 CS=370, SC=371이다. 기존 번호를 이동하거나 재사용하지 않는다.
- 서버 기준 정의는 `CombatReportPackets.h`이며 sizeof/offset static_assert로 크기를 고정한다.

## CS_COMBAT_REPORT_REQUEST

전체 **18바이트**.

| 오프셋 | 타입 | 이름 | 의미 |
| --- | --- | --- | --- |
| 0 | uint16 | size | 18 |
| 2 | uint16 | type | 370 |
| 4 | uint32 | requestId | 클라이언트가 발급하는 요청 식별자, 그대로 응답 |
| 8 | uint32 | roomId | 현재 방 ID |
| 12 | uint32 | lifeId | 첫 페이지는 0, 이후 성공 응답의 값 |
| 16 | uint16 | pageIndex | 0부터 시작 |

lifeId는 라운드 번호가 아니라 세션 내 기록 세대다. 방 변경이나 부활에도 바뀌므로 직접 계산하지 않는다. lifeId=0은 pageIndex=0에서만 허용한다.

예: requestId=1, roomId=42, lifeId=0, pageIndex=0:

```text
12 00 72 01 01 00 00 00 2A 00 00 00 00 00 00 00 00 00
```

## SC_COMBAT_REPORT

성공·실패 모두 전체 **512바이트**. 고정 헤더 32바이트 + Entry 60바이트 × 8개다. 사용하지 않은 Entry와 reserved는 0이다.

| 오프셋 | 타입 | 이름 | 의미 |
| --- | --- | --- | --- |
| 0 | uint16 | size | 512 |
| 2 | uint16 | type | 371 |
| 4 | uint32 | requestId | 요청 식별자 |
| 8 | uint8 | version | 1 |
| 9 | uint8 | status | 아래 상태 코드 |
| 10 | uint8 | flags | bit0 사망 기록 고정, bit1 용량/카운터 한도 도달 |
| 11 | uint8 | entryCount | 이 페이지의 유효 Entry 수, 0~8 |
| 12 | uint32 | roomId | 성공 시 기록의 방 ID |
| 16 | uint32 | lifeId | 성공 시 기록 세대 |
| 20 | uint32 | killerId | 자신을 처치한 playerId, 없으면 0 |
| 24 | uint16 | pageIndex | 요청 페이지 |
| 26 | uint16 | pageCount | 성공 시 1~16, 빈 기록도 1 |
| 28 | uint16 | totalEntries | 전체 집계 행 수, 0~128 |
| 30 | uint16 | reserved | 0 |
| 32 | Entry[8] | entries | 아래 구조, entryCount개만 사용 |

| status | 의미 | 클라이언트 처리 |
| --- | --- | --- |
| 0 | 성공 | version=1과 크기·개수 검증 후 사용 |
| 1 | 조회 불가 | 살아 있음, 관전자, 해당 방 소속 아님, 고정 기록 없음 등. UI에 기존 기록을 덧붙이지 않음 |
| 2 | 오래된 기록 | lifeId/기록 방 불일치. 해당 페이지 요청을 폐기 |
| 3 | 잘못된 페이지 | 범위 초과 또는 lifeId=0으로 추가 페이지 요청 |

실패 응답은 header/requestId/version/status/pageIndex 외 모두 0이다. flags bit1이 있으면 일부 기록이 생략되었을 수 있으므로 완전한 총계라고 표시하지 않는다. 카운터는 uint32 최대값에서 포화되고 wrap하지 않는다.

## Entry

행 기준 오프셋. 유일 키는 `(opponentId, direction, sourceKind, sourceId)`다. 표시명·캐릭터는 해당 행을 처음 기록했을 때 저장한다.

| 오프셋 | 타입 | 이름 | 의미 |
| --- | --- | --- | --- |
| 0 | uint32 | opponentId | 교전 상대 playerId |
| 4 | int32 | characterId | 상대의 lockedCharacterId, 미확정이면 -1 |
| 8 | byte[20] | nickname | 기존 SC_DIE와 같은 인코딩, NUL까지 디코딩 |
| 28 | uint8 | sourceKind | 0 무기, 1 스킬 |
| 29 | uint8 | direction | 0 내가 준 피해, 1 내가 받은 피해 |
| 30 | uint16 | reserved | 0 |
| 32 | int32 | sourceId | 무기 ID 또는 아래 스킬 ID |
| 36 | uint32 | hpDamage | 실제 체력 감소 누계 |
| 40 | uint32 | barrierDamage | 실제 보호막 감소 누계 |
| 44 | uint32 | bodyHits | 몸통 명중 이벤트 수 |
| 48 | uint32 | headHits | 머리 명중 이벤트 수 |
| 52 | uint32 | legHits | 다리 명중 이벤트 수 |
| 56 | uint32 | unlocalizedHits | 스킬 등 부위 없는 피해 이벤트 수 |

스킬 ID는 리포트 전용 값이며 무기 ID, 스킬 슬롯 번호, 캐릭터 ID와 혼용하지 않는다.

| sourceKind | sourceId | 표시 |
| --- | --- | --- |
| 0 | 기존 ServerWeaponId | 기존 무기 이름·아이콘 사용 |
| 1 | 1 | 이니시에이터 드론 테이저 |
| 1 | 2 | 이니시에이터 궁극기 |
| 1 | 3 | 엔트리 블레이드 |
| 1 | 4 | 센티널 궁극기 |

피해를 주지 않는 스캔·연막·상태이상·장치 자체의 HP 감소는 포함하지 않는다. 새 스킬 피해 경로를 추가하면 공통 ApplyDamage 기록 연결과 새 sourceId가 필요하다. 공격자가 이미 퇴장한 센티널 지속 효과도 피해를 기록하며, 이때 상대 메타데이터를 조회할 수 없으면 characterId=-1, nickname은 빈 문자열이다. UI는 기본 아이콘과 대체 이름을 사용한다.

명중 수는 실제 양의 피해가 적용된 이벤트 수다. 산탄총 펠릿이나 지속 피해 틱은 발사 버튼을 누른 횟수와 같지 않으므로 공통 UI 라벨은 **명중 횟수** 또는 **피해 횟수**로 표시한다. body/head/legs만 합쳐 스킬 틱을 총알 명중으로 세지 않는다.

## 화면 집계 예

상대별로 direction=0의 hpDamage+barrierDamage를 합산하면 준 피해, direction=1이면 받은 피해다. 방향별 hits도 합산한다. sourceKind/sourceId로 펼침 영역의 무기·스킬 세부 내역을 만든다. 한 피해가 보호막과 체력 모두에 적용돼도 명중 횟수는 1이다. 마지막 피해가 20이고 남은 체력이 10이면 피해 기록은 10이다.

상대가 killerId와 같으면 처치자 표시를 붙인다. 같은 상대가 여러 행에 등장하므로 행 개수를 상대 수로 표시하지 않는다. 빈 성공 응답은 오류가 아니며 '기록된 피해 없음'으로 처리한다. nickname 또는 characterId를 못 해석하면 기본 아이콘과 안전한 대체 이름을 사용한다.

## SW 구현 완료 기준

- 기존 SendHit(bool), 사격·이동·스킬·관전·기존 HUD 참조를 유지한다. UI는 씬/프리팹 Hierarchy에서 작성한다.
- 한 캐릭터에서 Body/Head/Legs가 실제 게임 콜라이더를 통해 정확히 전송되는지 먼저 확인한 후 나머지 캐릭터에 적용한다.
- 본인 사망에만 요청하고, 관전 대상 변경에는 본인 기록이 유지된다.
- 보호막만 맞은 경우, 머리·다리 혼합, 여러 상대·무기·스킬, 빈 기록, 여러 페이지, 스킬 사망을 표시한다.
- 라운드 리셋·부활·퇴장 시 숨기고, 늦은 응답·중복 응답을 무시한다. 성공한 동일 페이지를 중복 합산하지 않는다.
- 새 서버 + 기존 클라이언트는 요청 370을 보내지 않으므로 응답 371도 받지 않는다. 새 클라이언트 + 이전 서버는 응답이 없을 수 있으므로 타임아웃으로 처리한다.

## 서버 검증 실행

`Tests/CombatReportTests.vcxproj`는 실제 dispatcher, Session, loopback socket을 사용하는 분리 테스트다. 실행 인자는 **아직 존재하지 않는 저장소 밖 경로**여야 한다. 테스트가 그곳에 전용 계정 파일을 만들며 기존 계정 데이터를 사용하지 않는다. OutDir와 IntDir도 저장소 밖으로 지정한다.

기본 테스트는 기록 집계·페이지·상한·동시 기록·무효 부위·피해량·보호막·사망 통계·권한·초기화·실제 응답 프레임을 검증한다. 스킬은 공통 기록 함수의 4개 sourceId를 검증하며, 모든 스킬 시전·충돌 연출을 실제 Unity에서 실행하는 테스트를 대신하지 않는다. `RegressionSource=MatchLifecycleTests.cpp`로 같은 프로젝트를 별도 출력 경로에 빌드하면 기존 매치 정산·파티 회귀 테스트를 실행할 수 있다.

`Tests/ValidateCombatReportContract.py`는 패킷 번호 중복, 바이트 수, 요청 예제, 모든 기존 피해 경로 연결과 초기화 위치를 읽기 전용으로 검증한다.

### 검증 결과

- 2026년 10월 13일: Windows x64 Release 서버 빌드 성공.
- 전투 리포트 단위·loopback 통합 테스트 `COMBAT_REPORT_PASS` 통과. 기존 헤드샷/몸통 데미지, KDA, 아군 피격 차단과 구형 클라이언트에 대한 비자동 발송을 함께 검증했다.
- 패킷/연결 정적 검사 `COMBAT_REPORT_CONTRACT_PASS` 통과.
